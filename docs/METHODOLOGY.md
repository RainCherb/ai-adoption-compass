# Методология расчёта

Документ описывает, **как именно** Compass оценивает процессы и подбирает модели. Все параметры вынесены в YAML
(`src/adoption_compass/data/*.yaml`) и переопределяются без правки кода — см. [«Калибровка»](#калибровка-под-свою-компанию).

> Расчёт — это **оценка на основе допущений**, а не прогноз и не гарантия результата. Его задача — упорядочить
> гипотезы и показать, какие допущения важнее всего, а не заменить пилот.

## 1. Что подаётся на вход

Каждый процесс описывается строкой CSV (или JSON-объектом в API):

| Поле | Смысл |
| --- | --- |
| `runs_per_month`, `minutes_per_run` | сколько раз в месяц и сколько минут человек тратит на одну операцию |
| `hourly_cost_rub` | полная стоимость часа сотрудника (если не задана — 800 ₽) |
| `task_type` | тип задачи для ИИ: классификация, извлечение, резюмирование, подготовка текстов, ответы по базе знаний, перевод, анализ, код, поддержка решений |
| `error_rate`, `error_cost_rub` | доля операций с ошибкой сегодня и стоимость одной ошибки |
| `standardization` (1–5) | насколько операция повторяется по шаблону |
| `digital_readiness` (1–5) | насколько входные данные уже оцифрованы и доступны |
| `risk_level` (1–5) | цена ошибки модели: от «поправим» до «юридические или финансовые последствия» |
| `data_sensitivity` | `public` / `internal` / `confidential` / `personal` |
| `must_self_host` | требование ИБ: данные не покидают контур компании |
| `tokens_in`, `tokens_out` | необязательно: объём токенов на операцию (иначе — типовой для задачи) |

## 2. Экономия времени

```
hours             = runs_per_month × minutes_per_run / 60
standardization_f = 0.55 + 0.45 × (standardization − 1) / 4          # 0.55 … 1.00
digital_f         = 0.50 + 0.50 × (digital_readiness − 1) / 4        # 0.50 … 1.00
automation_share  = base_automation[task_type] × standardization_f × digital_f
review_share      = min(0.6, review_overhead[task_type] + 0.05 × (risk_level − 1))
net_share         = automation_share × (1 − review_share)
hours_saved       = hours × net_share
```

* `base_automation` — доля ручного времени, которую ИИ снимает **в идеальных условиях** (классификация — 0,70,
  поддержка решений — 0,25).
* Чем хуже стандартизация и оцифрованность, тем меньше реально снимается.
* `review_share` — часть сэкономленного времени уходит на проверку результата человеком; чем выше риск, тем больше.

## 3. Деньги

```
savings        = hours_saved × hourly_cost_rub
error_savings  = runs × error_rate × error_cost_rub × error_reduction          # error_reduction = 0.25
llm_cost       = стоимость выбранной модели при токенах × llm_overhead          # llm_overhead = 1.3
implementation = min(60, base_days[task_type] × m_digital × m_risk × m_sensitivity) × 25 000 ₽
support        = 2 % от implementation в месяц
```

| Множитель трудоёмкости | значения |
| --- | --- |
| `m_digital` (оцифрованность 1…5) | 1,5 · 1,5 · 1,2 · 1,0 · 1,0 |
| `m_risk` (риск 1…5) | 1,0 · 1,0 · 1,0 · 1,2 · 1,5 |
| `m_sensitivity` | публичные и внутренние — 1,0; конфиденциальные и персональные — 1,25 (обезличивание, self-hosted, согласования) |

Показатели за горизонт `H` месяцев (по умолчанию 12):

```
net_month    = savings + error_savings − llm_cost − support
payback      = implementation / net_month            (если net_month > 0)
net_horizon  = net_month × H − implementation
ROI          = net_horizon / (implementation + (llm_cost + support) × H)
```

### Сценарии

Те же формулы пересчитываются с множителями (экономия / стоимость LLM / внедрение):

| Сценарий | экономия | LLM | внедрение |
| --- | --- | --- | --- |
| Пессимистичный | ×0,6 | ×1,5 | ×1,3 |
| Базовый | ×1,0 | ×1,0 | ×1,0 |
| Оптимистичный | ×1,25 | ×0,8 | ×0,9 |

Если проект окупается и в пессимистичном сценарии — риск невысок; если только в оптимистичном — это ставка.

## 4. Приоритизация

Три оценки по шкале 0–100:

```
fit      = 100 × (0.40 × min(1, base_automation / 0.70) + 0.25 × (standardization − 1)/4
                  + 0.20 × (digital_readiness − 1)/4 + 0.15 × (5 − risk)/4)
impact   = 100 × (1 − exp(−max(net_horizon, 0) / 500 000 ₽))          # насыщающая шкала
ease     = 100 × (0.50 × (1 − min(days, 40)/40) + 0.25 × (digital_readiness − 1)/4
                  + 0.25 × (5 − risk)/4)
priority = 0.5 × impact + 0.3 × ease + 0.2 × fit
```

Квадрант определяется по порогам `impact ≥ 50` и `ease ≥ 50`:

| Квадрант | Условие | Волна дорожной карты |
| --- | --- | --- |
| **Быстрая победа** | эффект высокий, внедрение простое | 1 |
| **Стратегический проект** | эффект высокий, внедрение сложное | 2 |
| **Попутная задача** | эффект небольшой, внедрение простое | 3 |
| **Отложить** | `net_horizon ≤ 0` или эффект и простота ниже порогов | — |
| **Нет допустимой модели** | ни одна модель не проходит политику данных и порог качества | — |

### Блокировки

Для задач с `risk_level ≥ 4` требуемое качество модели повышается на единицу. Если после этого ни одна модель,
допустимая политикой данных, не дотягивает — процесс получает статус «Нет допустимой модели» и приоритет 0.
Для `decision_support` с персональными данными дополнительно выставляется критичное предупреждение: решения о людях
нельзя принимать только по ответу модели (согласуйте формулировки с юристом).

## 5. Общая инфраструктура self-hosted

У self-hosted модели нет платы за токены, но есть **фиксированные расходы** на GPU-серверы и ограниченная ёмкость.

1. Модель для каждого процесса выбирается по цене «в одиночку» (сервер целиком на один процесс).
2. Процессы, выбравшие один и тот же сервер, делят его стоимость **пропорционально токенам**; число серверов растёт
   ступенями по ёмкости (`capacity_mtok_month`).
3. Процесс, который с учётом своей доли убыточен, **исключается** из общего пула — остальные считаются заново.
   Так продолжается, пока состав не стабилизируется. Исключённый процесс показывается так, будто подключается
   к уже работающему серверу.

Поэтому self-hosted окупается там, где есть сразу несколько крупных процессов или жёсткое требование ИБ.

## 6. Подбор модели

### Жёсткие ограничения (модель исключается с понятной причиной)

1. **Политика данных:** сочетание «категория данных — размещение модели» запрещено (например, персональные данные
   и зарубежное облако).
2. Зарубежные облака отключены ограничением заказчика.
3. Требуется self-hosted.
4. Доступ из РФ возможен только через обходные пути, а они не разрешены.
5. Нет нужной возможности: изображения, вызов функций, контекстное окно.
6. Оценка качества для типа задачи ниже порога.
7. Месячная стоимость превышает бюджет.

Если подходящих моделей нет, советник перечисляет, **что именно ослабить** (качество, бюджет, обходные пути…),
и какие модели тогда подойдут. Политику данных ослаблять он не предлагает никогда.

### Ранжирование оставшихся

Оценка модели — взвешенная сумма четырёх компонентов (0–1):

| Профиль | качество | цена | безопасность | доступность из РФ |
| --- | --- | --- | --- | --- |
| Баланс | 0,40 | 0,25 | 0,20 | 0,15 |
| Минимальная цена | 0,25 | 0,50 | 0,15 | 0,10 |
| Максимальное качество | 0,60 | 0,10 | 0,15 | 0,15 |
| Максимальная безопасность | 0,25 | 0,10 | 0,50 | 0,15 |

* **Качество** — «достаточно хорошо»: `min(q, порог) + w × max(0, q − порог)`, где `w` = 0,5 для баланса и
  безопасности, 0,25 для цены и 1,0 для качества. Так лишняя звезда не оправдывает тройную цену.
* **Цена** — логарифмическая шкала среди подходящих: самая дешёвая получает 1, самая дорогая — 0.
* **Безопасность** — из матрицы `safety_scores` в `policy.yaml` (self-hosted всегда лучше или равен).
* **Доступность** — 1,0 для прямого доступа и 0,3 для обходных путей.

Стоимость: `токены × цена` (+ `фиксированные расходы × число блоков ёмкости` для self-hosted); цены в USD
переводятся по курсу из допущений.

## 7. Пример

Процесс: 1000 операций в месяц по 6 минут, час стоит 1000 ₽, классификация публичных данных,
стандартизация 5, оцифрованность 5, риск 1, модель без запаса токенов.

| Шаг | Значение |
| --- | --- |
| Трудозатраты | 100 ч/мес |
| `automation_share` | 0,70 × 1,0 × 1,0 = 0,70 |
| `net_share` | 0,70 × (1 − 0,10) = 0,63 → **63 ч/мес** |
| Экономия | 63 ч × 1000 ₽ = **63 000 ₽/мес** |
| Внедрение | 6 дней × 25 000 ₽ = **150 000 ₽** |
| Сопровождение | 2 % × 150 000 = 3 000 ₽/мес |
| Модель | YandexGPT Pro-класс, 1000 × 760 токенов = **304 ₽/мес** |
| `net_month` | 63 000 − 304 − 3 000 = **59 696 ₽** |
| Окупаемость | 150 000 / 59 696 = **2,51 мес.** |
| Эффект за 12 мес. | 59 696 × 12 − 150 000 = **566 352 ₽** (ROI 299 %) |
| Сценарии (12 мес.) | пессимистичный 206 328 ₽ · оптимистичный 774 682 ₽ |
| Оценки | fit 100 · impact 67,8 · ease 92,5 · priority 81,6 → **быстрая победа** |

Эти числа проверяются автотестом `tests/test_assessment.py::test_numbers_follow_the_documented_formulas`.

## 8. Что модель не учитывает

Честные ограничения подхода — их стоит проговаривать заказчику:

* Сезонность и рост объёмов; одноразовые затраты на обучение сотрудников и управление изменениями.
* Качество данных внутри процесса и интеграции со старыми системами сверх множителя `digital_readiness`.
* Эффект от скорости и качества сервиса (удержание клиентов, меньше жалоб) — учитывается только через `error_cost_rub`.
* Рыночные цены, курсы и условия доступа меняются: встроенный каталог помечен как **демонстрационный**
  (`data_status: illustrative`), а `compass catalog check` напоминает о проверке.
* Оценки качества моделей (1–5) — стартовые экспертные значения; правильный путь — заменить их результатами
  `compass eval` на ваших данных.

## Калибровка под свою компанию

Положите свои версии файлов в каталог и укажите `COMPASS_DATA_DIR=./my-data` — они переопределят встроенные:

| Файл | Что настраивает |
| --- | --- |
| `scoring.yaml` | допущения, сценарии, пороги квадрантов, веса приоритета, профили задач, множители сложности |
| `catalog.yaml` | модели: цены, размещение, доступность из РФ, качество по задачам, дата проверки |
| `policy.yaml` | матрица «данные → размещение», оценки безопасности, правила «всегда / никогда» для памятки |
| `prompts.yaml` | библиотека шаблонов запросов |
| `evals/routing.yaml`, `evals/routing.jsonl` | задача и золотой набор для `compass eval` |

Все файлы проверяются схемами при загрузке — ошибка в данных не доживёт до расчёта.
